# 形式化证明工程化实验方案（修订版）

## 0. 修订说明

本修订版是在阅读 [Gemini的调研报告](d:\Codes\Math\hyperbolic_lean\docs\Gemini的调研报告.md)、[Doubao的调研报告](d:\Codes\Math\hyperbolic_lean\docs\Doubao的调研报告.md) 以及已有的 [形式化证明工程化初步实验方案](d:\Codes\Math\hyperbolic_lean\docs\形式化证明工程化初步实验方案.md) 后重写的版本。

与初版相比，这一版有六个关键更新：

1. **收紧主线问题**  
   初版同时推进“表达式级显式编码、形式化图谱、证明轨迹”三条主线，主题过宽。修订版明确把可投稿主线收束为：  
   **形式化数学图谱的双曲表示 + 性质 probing + 检索辅助证明**。

2. **把表达式级实验降级为支撑模块**  
   表达式重写审计器仍然保留，但定位从“并列主线”改为“低成本验证显式维度思想的前期试验台”。

3. **把 `γ` 无理性探索降级为远期探索，不再作为主项目目标**  
   两份调研都给出了很多启发，但从工程与投稿可行性看，`γ` 相关内容最多只能作为后期案例分析或附录式探索，不能作为主论文承诺。

4. **吸收了更具体的数据工程思路**  
   尤其是 LeanDojo、Graph2Tac、LeanProgress、Lean 元编程/类型类综合等方向带来的启发。  
   其中最值得吸收的是：**用 Lean 自己做标签抽取与验证，而不是靠文本规则硬猜。**

5. **增加阶段门（stage gate）和备选路径**  
   初版偏“路线图”；修订版加入了 go/no-go 判据、失败分支和降级投稿路线，避免项目在中途失控。

6. **加强严谨性约束**  
   修订版明确：
   - 不把 `synthInstance` 失败直接当作负标签
   - 不默认整个 Mathlib 都适合双曲建模
   - 不一开始就上最复杂的 HypHGT/长证明生成
   - 不把“几何解释”当作先验结论，而是当作待验证假设

## 1. 立项结论

### 1.1 最终建议

如果目标是做出**一项真实可执行、可复现、可投稿**的成果，那么最合理的项目定位应当是：

**构建一个面向 Lean/Mathlib 的形式化数学图谱表示学习平台，验证双曲表示是否比欧氏表示更适合建模其层级结构，并进一步评估这种表示是否有助于性质 probing 和 proof-hint retrieval。**

这条主线的优点是：

1. 有明确数据源  
   LeanDojo 和 Mathlib 已经提供了较干净的形式化语料基础。

2. 有自然任务闭环  
   图抽取、嵌入学习、性质预测、检索、Lean 验证可以构成可重复实验链路。

3. 有足够的新意但不过分冒进  
   “形式化数学图谱 + 双曲表示 + 性质 probing/检索”这个交叉点仍然比较稀缺，但比“自动发现未解难题证明”现实得多。

4. 便于形成论文叙事  
   论文可以围绕“数学形式化图谱具有层级友好的几何结构”展开，而不是被多个方向稀释。

### 1.2 不建议的主目标

以下方向在当前阶段不应作为主立项目标：

1. 自动证明 `γ` 无理性或其他开放问题
2. 直接构造端到端长证明生成系统
3. 先做全网自然语言自动形式化，再做双曲图谱
4. 同时把表达式显式编码、图谱嵌入、证明搜索、自然语言对齐都做成同等主线

## 2. 核心研究问题与非目标

### 2.1 核心研究问题

修订后建议聚焦四个研究问题。

### RQ1：Mathlib 声明图是否具有足够强的层级性，从而值得使用双曲表示？

这里不能先假定“数学知识一定适合双曲空间”，而是应先做结构诊断：

- DAG 深度统计
- ancestor/descendant 分布
- tree-likeness
- Gromov hyperbolicity 或近似层级性指标
- 不同子领域子图的结构差异

如果这一层证据不足，后续双曲建模的说服力会很弱。

### RQ2：在低维表示下，双曲模型是否优于欧氏模型？

重点不只是看最终准确率，还要看：

- 低维压缩下的性能保持
- 层级边的恢复能力
- 检索质量
- 结构失真

换言之，要证明的是：

**双曲空间不是“也能做”，而是在特定任务上更合适。**

### RQ3：形式化数学对象的某些性质能否在嵌入空间中被可靠 probe 出来？

例如：

- declaration type: `def/theorem/lemma/class/instance`
- 某些代数/拓扑类型类属性
- 某声明所属的数学子域或模块簇

这里要把“显式特征维度”从哲学直觉变成可测实验。

### RQ4：图谱表示是否能帮助 proof-hint retrieval，而不仅仅是做可视化？

如果最终只能画出漂亮的图，而不能提升任何与证明有关的检索或排序任务，论文价值会明显下降。

因此至少要验证以下一项：

- theorem retrieval
- proof-state nearest-neighbor retrieval
- tactic ranking
- compile-success 提升

### 2.2 非目标

本项目当前不试图证明：

1. 双曲空间一定能学出“真实的数学语义轴”
2. 嵌入空间的局部几何簇一定对应深层数学真理
3. 模型能自动发现开放问题证明
4. 表达式显式编码本身就足以支撑完整形式化证明

这些都只能作为探索性结论，而不是主论文 claim。

## 3. 修订后的总架构

修订版建议采用“一条主线 + 两个支撑模块”的结构。

### 3.1 主线模块 M：形式化数学图谱的双曲表示学习

这是主论文方向，包含：

1. Mathlib/LeanDojo 图数据抽取
2. 图结构诊断
3. 欧氏 baseline
4. 双曲 baseline
5. 性质 probing
6. retrieval 评估

### 3.2 支撑模块 S1：proof-state 检索与 tactic 轻量排序

这是与“证明”最近的一层，但仍然保持在检索/排序，而不是生成。

其作用是：

1. 让主线与自动定理证明社区更接轨
2. 为投稿提供更强的应用价值
3. 在不做长证明生成的前提下，验证表示是否真正有用

### 3.3 支撑模块 S2：表达式级多视角显式编码试验台

这一模块不作为主论文中心，而作为：

1. 显式特征思想的低成本验证器
2. 未来做 proof-state 多视角编码的原型来源
3. 若主线遇阻时的备用小成果产出点

### 3.4 远期探索模块 X：`γ` 等特殊常数案例分析

定位为：

1. 展示系统如何用于“数学研究启发”
2. 作为 future work 或附录案例

不定位为：

1. 论文主结果
2. 项目交付承诺

## 4. 数据工程方案

## 4.1 数据源与版本锁定

所有实验必须固定在单一、可复现的版本组合上：

- Lean 4 版本
- Mathlib commit
- LeanDojo 版本
- Python 环境与模型依赖版本

建议在项目启动时就生成：

1. `environment.yml` 或 `requirements.txt`
2. 数据抽取脚本版本号
3. 数据卡（data card）
4. 仓库 commit 记录表

否则后面图结构和标签会随着 Mathlib 更新而漂移，导致实验不可复现。

## 4.2 图对象的选择

初版不建议“一张大图包打一切”，而建议拆成三类图，逐层推进。

### 图 A：声明依赖图

节点：

- `def`
- `theorem`
- `lemma`
- `class`
- `instance`

边：

- declaration 使用 declaration
- theorem proof 中引用 declaration
- definition body 中引用 declaration

这是主线图。

### 图 B：类型类继承图

节点：

- typeclass
- instance
- 结构体

边：

- extends
- instance-of
- coercion-related relation

这是最有可能天然表现出层级结构的子图，应优先验证双曲优势。

### 图 C：proof-state 转移图

节点：

- proof state

边：

- tactic transition

这是后续 retrieval/tactic 任务的图基础，不必在最早阶段全量抽取。

## 4.3 标签抽取：吸收调研报告后的修正版

两份调研里最值得吸收的工程点，是**利用 Lean 元编程和类型类综合来提取标签**。  
但初版里有一个需要严格修正的地方：

**`synthInstance` 失败不能直接记为负标签。**

因为失败可能意味着：

1. 查询类型本身不适用于该声明
2. 实例搜索超时
3. 属性不可由 typeclass 直接表达
4. 当前环境缺少桥接实例

因此，标签必须采用**三值制**：

- `positive`
- `negative`
- `unknown`

### 4.3.1 推荐的标签来源

1. **结构性标签**
   - declaration kind
   - namespace/module
   - file path
   - whether theorem/definition/class

2. **类型类可综合标签**
   - `CommGroup`
   - `CommRing`
   - `Finite`
   - `CompactSpace`
   - 其他仅在查询类型正确且实例语义稳定时使用

3. **语法/复杂度标签**
   - AST 大小
   - proof 长度
   - dependency depth

### 4.3.2 推荐的标签策略

对每个候选属性 `P`：

1. 先判断该声明是否能形成合法查询
2. 若能合法查询且 `synthInstance` 成功，则标 `positive`
3. 若能合法查询且存在显式反例或显式不可满足证据，才标 `negative`
4. 其余全部标 `unknown`

对于 `negative` 难以稳定构造的属性，建议只做：

- `positive` vs `unlabeled`
- 或只在高置信子集上做二分类

这会牺牲一部分数据量，但会显著提高结论可信度。

## 4.4 数据切分策略

为避免泄漏，不能随机切声明。

建议优先尝试三种切分：

1. **模块切分**
   - 按 `Mathlib/Algebra/...`、`Mathlib/Topology/...` 等目录切

2. **时间切分**
   - 若能拿到不同版本轨迹，可按 commit 时间切

3. **边切分**
   - link prediction 时做边遮蔽，但必须保持训练图连通性

若只做随机切分，很容易学到文件级模式而非真正的结构泛化。

## 4.5 首批数据规模建议

不要一上来全量跑整个 Mathlib。

建议按以下顺序推进：

1. 类型类继承相关子图
2. `Algebra` + `Topology` 两个子域
3. 再扩展到更大全量声明图

这是因为：

1. 这些子图层级性更明显
2. 标签更容易抽
3. 更适合作为双曲表示的首批验证场景

## 5. 模型路线：先稳，再难

## 5.1 不要一开始就上最复杂模型

Gemini 报告中的 HypHGT/HypTransformer 类方向有吸引力，但对当前项目而言，**过早使用复杂模型只会增加调参难度和审稿质疑点**。

更合理的模型梯度是：

### 第一级：图启发式与浅层基线

- degree / PageRank / ancestor overlap
- BM25 / lexical retrieval
- Node2Vec / DeepWalk

作用：

1. 给出最小可比基线
2. 验证任务本身不是“随便做都很高分”

### 第二级：欧氏图模型

- GCN
- GraphSAGE
- GAT
- 简单的 graph transformer

作用：

1. 建立强欧氏 baseline
2. 为后续双曲模型提供公平对照

### 第三级：双曲模型

- Poincaré embedding
- HGCN
- Lorentz / hyperbolic GNN 变体

### 第四级：可选的高复杂模型

- HypHGT / Hypformer / 更复杂双曲 transformer

只有在前三级已经形成清晰证据时，才值得上这一级。

## 5.2 为什么这样分层

因为论文要回答的不只是“能不能做”，而是：

1. 简单欧氏方法做到哪一步
2. 双曲方法在哪个点开始带来优势
3. 这个优势是来自模型容量，还是来自几何归纳偏置

如果没有清晰的 baseline 梯度，审稿人很容易把所有收益归因于“模型更复杂”。

## 6. 实验任务设计

## 6.1 T0：图结构诊断

这是修订版新增的必做任务。

目标：

在投入双曲模型之前，先证明图结构至少部分具有双曲友好性。

指标：

- graph depth
- branching factor
- shortest-path statistics
- tree-distance distortion
- approximate Gromov hyperbolicity
- ancestor/descendant recovery difficulty

预期结论：

1. 不是整个 Mathlib 都一样层级化
2. 某些子图比另一些更适合双曲表示

这会直接决定后续实验该在哪些子图上做。

## 6.2 T1：声明依赖边的 link prediction

输入：

- 部分遮蔽后的声明依赖图

输出：

- 被遮蔽依赖边的预测排序

指标：

- MRR
- Hits@1 / Hits@10
- MAP
- AUROC

这是最标准、最容易形成主论文结果的任务。

## 6.3 T2：节点类型与性质 probing

任务分两类：

### 稳定标签任务

- `def/theorem/lemma/class/instance`
- module/domain 分类
- file-level family 分类

### 高价值标签任务

- `CommGroup` 类属性
- `CommRing`
- `Finite`
- `CompactSpace`

指标：

- macro F1
- AUROC
- calibration
- probe complexity sensitivity

这里建议加入：

1. 线性 probe
2. MLP probe

如果线性 probe 已经有效，说明表示空间更有解释力。

## 6.4 T3：检索任务

建议至少做两个：

### theorem retrieval

给定一个 theorem 或 goal 描述，检索相关声明。

### proof-state retrieval

给定当前 state，检索历史上相似 state 和成功 tactic。

基线：

- BM25
- dense text retrieval
- graph embedding retrieval
- graph + text hybrid retrieval

指标：

- Recall@k
- MRR
- nDCG
- top-k useful-hit rate

## 6.5 T4：轻量 tactic ranking

这不是长证明生成，而是：

给定 proof state 和候选 tactics，排序哪个更可能成功。

可以借鉴：

- Graph2Tac 的表示思路
- LeanProgress 这类 proof-progress 指标思路

指标：

- top-k accuracy
- MRR
- compile-success@k

如果这个任务能带来稳定提升，你的论文应用价值会明显增强。

## 6.6 T5：表达式级显式编码试验台

此任务不作为主论文核心，但建议保留。

作用：

1. 快速验证“多视角显式编码”是否能学到
2. 为后续 proof-state 多头表示提供先验

建议任务：

- `truth_preserved`
- `domain_preserved`
- `operator_changed`
- `structure_changed`
- `explicitness_delta`

这部分最好作为：

- 项目先导实验
- 或附录补充实验

## 7. 评价标准与阶段门

修订版最重要的增强之一，是加入明确阶段门。

## Gate A：数据可行性门

判据：

1. 成功锁定 Lean/Mathlib/LeanDojo 版本
2. 在一个子域上稳定抽取声明图
3. 生成不少于 `10k` 声明节点的结构化数据
4. 至少一种标签族能稳定抽取

若失败：

1. 缩到更小子图
2. 先只做声明类型分类与 link prediction
3. 暂停性质 probing

## Gate B：欧氏基线门

判据：

1. 欧氏图模型显著优于随机/浅层启发式
2. 至少一个任务形成稳定、可复现实验表格

若失败：

1. 说明任务定义或数据质量有问题
2. 先不进入双曲阶段

## Gate C：双曲价值门

判据：

以下至少满足其一：

1. 双曲模型在低维下优于欧氏模型
2. 双曲模型在相同精度下需要更少维度
3. 双曲模型在层级相关任务上显著更优

若失败：

1. 降级为“形式化数学图谱 benchmark / dataset / probing”论文
2. 将双曲部分降为附加实验，而非中心 claim

## Gate D：应用价值门

判据：

1. 检索或 tactic ranking 至少有一个子任务优于文本基线
2. 或至少能证明图表示提供互补信息

若失败：

主论文仍可投稿，但故事线应转为：

**formal math graph representation benchmark**

而不是 proof assistance。

## 8. 从立项到投稿的执行计划

这里给出一条更稳妥的 `36 周主路径 + 8 周缓冲` 计划。

## 阶段 0：立项与复现实验准备（第 1-2 周）

目标：

1. 锁定版本
2. 明确研究 claim
3. 明确资源边界

交付物：

- 项目章程
- 技术栈清单
- 资源预算
- 版本锁定文件

## 阶段 1：数据抽取试运行（第 3-6 周）

目标：

1. 跑通 LeanDojo
2. 先在小子域上抽图
3. 验证能否拿到 declaration-level 结构

交付物：

- 小规模图样本
- 抽取脚本
- 数据字段说明

阶段门：

- Gate A

## 阶段 2：数据集正式构建（第 7-10 周）

目标：

1. 构造主图
2. 构造可靠标签
3. 做初步统计分析

交付物：

- 主图数据集 v1
- 标签数据集 v1
- 图结构统计报告

## 阶段 3：欧氏 baseline（第 11-14 周）

目标：

1. 先把任务做通
2. 建立强 baseline

交付物：

- heuristic baseline
- Node2Vec/GCN/GraphSAGE 结果
- baseline 表格 v1

阶段门：

- Gate B

## 阶段 4：双曲 baseline（第 15-20 周）

目标：

1. 跑通 Poincaré/HGCN
2. 比较维度-性能曲线
3. 确认双曲是否真的有价值

交付物：

- 双曲实验表格
- 维度压缩对比图
- 双曲 vs 欧氏误差分析

阶段门：

- Gate C

## 阶段 5：probes 与 retrieval（第 21-26 周）

目标：

1. 做稳定的 node/property probing
2. 做 theorem/proof-state retrieval
3. 若可行，再加 tactic ranking

交付物：

- probing 结果
- retrieval 结果
- demo 原型

阶段门：

- Gate D

## 阶段 6：消融、稳健性与失败案例（第 27-30 周）

目标：

1. 做 ablation
2. 做不同子图对比
3. 整理失败案例

必须做的消融：

1. 图类型消融
2. 标签族消融
3. 维度消融
4. 文本特征与图特征的融合消融
5. 双曲曲率/模型复杂度消融

交付物：

- ablation 表
- 误差分析报告
- 失败案例附录

## 阶段 7：论文写作与投稿包准备（第 31-36 周）

目标：

1. 写论文
2. 整理开源材料
3. 形成投稿包

投稿包应包含：

1. 主论文
2. appendix
3. artifact README

## 12. 对旧版方案的最终修正结论

综合两份调研报告后，我认为旧版方案最需要修正的地方有四点：

1. **主线要更窄**  
   旧版把三个方向并列推进，风险太大。

2. **标签要更谨慎**

3. **模型梯度要更稳**  
   旧版容易让人直接跳到复杂双曲 transformer。  
   修订后：先浅层，再欧氏，再双曲，再高复杂模型。

4. **投稿路径要前置设计**  
   旧版讲了实验，但对主张强度与投稿梯度约束不够。  
   修订后：加入 stage gate、备选故事线和 venue 梯度。

## 16. 默认评测协议与欧氏扩展补充

在完成真实样本的 `closed-world` 原型实验后，当前已经进一步将 harder negatives 固化为默认评测协议，并在该协议下完成了第一版真正可训练的欧氏 GCN baseline。

### 16.1 默认评测协议

当前建议将以下设置固化为默认协议：

1. 使用 `closed-world` declaration graph。
2. 默认 harder negatives 使用 `same_module`，并允许少量 `random fallback`。
3. 负采样 seed 使用稳定映射，不再依赖 Python `hash()`。
4. 所有后续欧氏/双曲模型优先在这一协议下比较，再决定是否补充 easy-negative 结果。

### 16.2 当前欧氏扩展结果

在上述默认协议下，已经完成：

- 默认协议 Node2Vec：`test AP = 0.5580`
- 默认协议纯 PyTorch GCN：`test AP = 0.9013`

这说明在更严格、更可信的评测设置下，欧氏图神经网络已经能够明显优于浅层随机游走嵌入，因而可以作为后续双曲模型的强对照基线。

### 16.3 对后续阶段的影响

这会带来三个直接变化：

1. 之后的双曲 baseline 不应再只对比随机负采样下的 Node2Vec，而应至少对比默认协议下的 GCN。
2. 若双曲方法不能稳定超过该 GCN，则论文主张应更保守，转向“formal graph benchmark + geometry-aware analysis”。
3. 下一轮最值得投入的是：在默认协议下补齐更完整的欧氏 baseline 组，并在同协议下引入双曲方法。

### 16.4 默认协议下的第一版双曲 baseline

在上述默认协议下，当前已经补齐了第一版可真实训练的纯 PyTorch 双曲 baseline，并完成了与 GCN 的同口径对照。

本轮双曲 baseline 的实现特征如下：

1. 仍然使用 `closed-world + same_module harder negatives (+ random fallback)`。
2. 编码器采用“切空间聚合 + Poincare ball 投影”的两层结构。
3. 链路预测解码器使用双曲距离打分。
4. 为保证数值稳定性，训练中加入了更稳的 `acosh` 距离实现、ball 内投影、有限值检查与梯度裁剪。

在真实 `lean4-example` 样本上的结果为：

- 默认协议双曲 baseline：`val AP = 0.4194`
- 默认协议双曲 baseline：`test AP = 0.4196`
- 默认协议双曲 baseline：`test AUROC = 0.3825`
- 最优验证轮次：`epoch 45`

与当前对照组比较：

- Node2Vec：`test AP = 0.5580`
- 纯 PyTorch GCN：`test AP = 0.9013`
- 双曲 baseline v1：`test AP = 0.4196`

### 16.5 这一结果对方案书的含义

这一轮结果很关键，因为它提供了一个真实但克制的结论：

1. 双曲 baseline 的工程链路已经打通，不再停留在概念层面。
2. 但在当前 declaration-graph、当前 harder-negative 协议和当前模型规模下，第一版双曲模型明显落后于现有 GCN。
3. 因而现阶段不能把“formal graph 天然更适合双曲建模”当作既成事实，只能把它保留为待进一步验证的研究假设。

这意味着后续双曲阶段需要从“是否能跑”转向“为什么当前不占优，以及在什么条件下才可能占优”。更具体地，后续最值得优先推进的是：

1. 低维对照实验，检查双曲方法是否在更小维度下更有压缩优势。
2. 子图分层实验，优先放到更明显层级化的类型类图或 inheritance 子图上验证。
3. 更合适的双曲模型设计，例如更强的双曲解码器、Lorentz 变体或节点特定曲率策略。
4. 更严格切分协议，例如模块切分或时间切分，避免当前边级切分掩盖真实泛化差异。

因此，当前最稳妥的论文叙事应继续以“formal graph benchmark + geometry-aware analysis”为主，而不是过早承诺“双曲一定优于欧氏”。如果后续更精细的双曲实验能够在低维、层级子图或 retrieval 任务中形成清晰优势，再把双曲提升为中心 claim 会更稳健。

### 16.6 低维对照与曲率扫描补充

为了进一步回答“双曲方法是否在低维下更合适”这一核心问题，当前已经补做了一轮第一版双曲模型的低维对照与曲率扫描。扫描设置如下：

1. 模型：第一版 `poincare_gcn_v1`
2. 维度：`8 / 16 / 32`
3. 曲率：`0.5 / 1.0 / 2.0`
4. 协议：仍然固定为 `closed-world + same_module harder negatives`
5. 训练预算：统一缩短到 40 epoch，用于快速筛选工作区间

当前扫描结果显示出两个重要现象：

1. 第一版双曲模型并不是维度越大越好，反而在 `8 维` 时表现最好。
2. 在当前样本上，`curvature = 1.0` 是最稳定的工作点，明显优于 `2.0`，也通常略优于 `0.5`。

扫描中最优组合为：

- `dim = 8`, `curvature = 1.0`
- `val AP = 0.4798`
- `test AP = 0.4800`
- `test AUROC = 0.4621`

这说明一个对方案书很重要的结论：即便第一版双曲模型整体不强，它在“低维压缩”这件事上已经开始表现出与欧氏直觉不同的行为模式，因此“低维性能保持”仍然值得作为双曲路线的保留观察指标，而不能只看单一的 32 维点位结果。

### 16.7 更强双曲版本：HGCN 风格第二版

在完成低维/曲率扫描后，当前已经进一步补了一版更强的双曲模型，记为 `hgcn_residual_v2`。它相对第一版的主要增强包括：

1. 使用更强的残差式切空间聚合，而不只是简单两层映射。
2. 加入 `LayerNorm` 与更稳定的非线性，减轻训练初期数值不稳定。
3. 链路预测解码器不再只依赖单一双曲距离，而是结合切空间边特征的 MLP 与距离项进行打分。

在默认协议、默认 32 维配置下，该版本已取得：

- `val AP = 0.7393`
- `test AP = 0.7374`
- `test AUROC = 0.7511`

这说明第二版双曲模型已经显著优于：

- 第一版双曲 baseline：`test AP = 0.4250`
- 默认协议 Node2Vec：`test AP = 0.5580`

但仍然落后于当前纯 PyTorch GCN：

- 纯 PyTorch GCN：`test AP = 0.9013`

### 16.8 第二版双曲模型的小范围扫描结论

为了避免把第二版结果建立在单一点位上，当前又对 `hgcn_residual_v2` 做了一轮较小范围的扫描：

1. 输出维度：`16 / 32`
2. 曲率：`0.5 / 1.0 / 2.0`
3. 训练预算：40 epoch 快速筛选

这轮结果进一步表明：

1. `32 维` 版本整体优于 `16 维` 版本。
2. `curvature = 0.5` 与 `1.0` 都明显优于 `2.0`。
3. 在压缩预算下，最佳点为 `dim = 32, curvature = 1.0`，其 `test AP = 0.7229`。

与此同时，第二版模型还暴露出一个新的工程信号：它的 `AP/AUROC` 已经较高，但在固定 `0.5` 阈值下 `F1` 很低，说明当前模型的排序能力提升快于概率校准能力。换言之，这一版本已经可以较好地区分正负边，但输出分数的绝对刻度仍需后续做 calibration 或阈值协议补充。

### 16.9 对后续双曲路线的直接启示

基于这一轮真实实验，双曲路线的后续推进应比此前更具体：

1. 第一版双曲模型的重点不再是继续放大维度，而是围绕低维优势和曲率敏感性做更系统的对照。
2. 第二版双曲模型已经证明“只要模型设计更合理，双曲方法可以显著超过浅层 baseline”，因此双曲路线不应被过早放弃。
3. 但由于它仍未超过当前 GCN，主论文仍不宜宣称“双曲优于欧氏”，而应表述为“在 formal graph 上，双曲方法对低维表示和几何敏感性具有可验证信号，并且在更强模型设计下可明显缩小与强欧氏基线的差距”。
4. 下一轮最值得投入的是：
   - 双曲模型的校准与阈值协议
   - 更层级化子图上的对照
   - 与 8/16/32 维欧氏 GCN 的严格低维公平比较

### 16.10 补充评测协议：temperature scaling + validation-max-F1 threshold

在上一轮实验中，第二版双曲模型虽然 `AP/AUROC` 较高，但固定 `0.5` 阈值下 `F1 = 0`，这使得它与 GCN 的 `F1` 无法直接比较。为解决这一问题，当前已经补上统一的后处理协议：

1. 先在 validation split 上做 temperature scaling。
2. 再在校准后的 validation 概率上选择使 `F1` 最大的阈值。
3. 将该温度和阈值原样应用到 test split。

这意味着后续 `F1` 不再依赖任意的固定 `0.5` 阈值，而是依赖一个明确、可复现、且对所有模型一致的 validation-driven 协议。

在这一协议下，当前默认 32 维第二版双曲模型的结果变为：

- 原始 `test AP = 0.7457`
- 原始 `test F1 = 0.0000`
- 校准后阈值：`0.3850`
- 校准温度：`103.24`
- 校准后 `test F1 = 0.7089`

这说明前一轮 `F1 = 0` 并不是模型完全不会区分正负边，而是概率刻度严重失配导致固定阈值评测失真。因此，在后续所有欧氏/双曲比较中，`F1` 都应优先报告这一“校准后阈值协议”下的结果。

### 16.11 同口径低维 GCN 对照

为了真正检验“低维双曲优势”，当前已经在完全相同的数据协议下补做了一组低维 GCN 对照实验：

1. 图：`closed-world`
2. 负例：`same_module harder negatives`
3. 维度：`8 / 16 / 32`
4. 训练预算：40 epoch
5. 后处理：与双曲模型相同的 temperature scaling + validation-max-F1 threshold

GCN 低维结果如下：

- `GCN-8d`：`test AP = 0.8653`，校准后 `test F1 = 0.7494`
- `GCN-16d`：`test AP = 0.8993`，校准后 `test F1 = 0.8064`
- `GCN-32d`：`test AP = 0.8977`，校准后 `test F1 = 0.8019`

与当前双曲结果对照：

- 第一版双曲最佳低维点：`8d, curvature=1.0, test AP = 0.4800`
- 第二版双曲默认点：`32d, test AP = 0.7457, calibrated test F1 = 0.7089`

这一轮对照给出的结论非常明确：

1. 在当前 declaration graph 与当前评测协议下，没有观察到“低维双曲明显优于低维欧氏 GCN”的证据。
2. 即便在 `8 维` 这个最有利于双曲叙事的点位上，GCN 仍然以很大幅度优于第一版双曲模型。
3. 更强的第二版双曲模型已经能显著超过 Node2Vec，并把 calibrated `F1` 提升到可比较区间，但仍未达到低维 GCN 的性能水平。

因此，当前最严谨的表述不应再是“低维下双曲优于欧氏”，而应是：

**在当前 formal declaration graph benchmark 上，双曲方法确实表现出低维敏感性与几何参数效应，但尚未形成超越强欧氏 GCN 的决定性证据。**

这一结论会直接影响论文主张强度，也进一步说明后续双曲路线应优先转向：

1. 更层级化的子图，而不是混合 declaration graph 全图。
2. 更强的双曲模型设计与更稳的校准协议。
3. 更关注“参数效率/几何诊断/子图适配性”，而不是笼统地宣称双曲全局更优。

### 16.12 将默认协议搬到更层级化子图：typeclass-like subgraph v1

为回应“全 declaration graph 可能过于混杂，不利于双曲结构显现”这一问题，当前已经基于现有 `declarations.csv + edges.csv` 抽出了一版更层级化的子图：`typeclass-like subgraph v1`。

需要强调的是，这一版还不是 Lean 内核级的精确 typeclass / inheritance 图，而是一张**工程上诚实、可复现、且可直接复用现有 baseline 协议**的近似子图。其构造规则为：

1. 节点只保留 `class / instance / structure` 三类声明。
2. 保留这些节点之间原有的 `uses` 边。
3. 从 `signature_text` 中额外正则抽取：
   - `extends_inferred`
   - `instance_of_inferred`

因此，这张图更准确的名称是：

**typeclass-like hierarchical subgraph**

而不是“完全精确的 inheritance graph”。

### 16.13 当前子图规模与边组成

在 `lean4_example_closed_world` 上，这张子图的当前规模为：

- 节点数：`1233`
- 边数：`990`

其中边类型分布为：

- `uses = 765`
- `extends_inferred = 120`
- `instance_of_inferred = 105`

节点类型分布为：

- `class = 2`
- `instance = 86`
- `structure = 1145`

这说明当前子图已经不再只是“class/instance 节点诱导出来的极稀疏 uses 图”，而是至少补上了一批明确与层级结构更相关的语义边。  
但也必须看到，它依然偏小，导致 val/test split 只有 `176` 个样本规模，因此所有结论目前都应视为“方向性证据”，而不是最终投稿级证据。

### 16.14 默认协议在子图上的第一轮对照

当前已将与全图相同的默认协议直接搬到这张子图上：

1. 边级 link prediction
2. `same_module harder negatives`
3. calibration / threshold 协议与全图完全一致

在该子图上的第一轮结果为：

- `GCN`：`test AP = 0.8578`
- `GCN calibrated test F1 = 0.7117`
- `HGCN v2`：`test AP = 0.7313`
- `HGCN v2 calibrated test F1 = 0.6920`

### 16.15 这一轮子图结果的含义

这轮结果比全图更值得关注，因为它提供了一个更细的信号：

1. 在 typeclass-like 子图上，双曲第二版依然没有超过欧氏 GCN。
2. 但与全 declaration graph 相比，双曲与 GCN 的差距有所缩小。
3. 特别是在校准后的 `F1` 上，当前二者已经接近：
   - `GCN calibrated test F1 = 0.7117`
   - `HGCN v2 calibrated test F1 = 0.6920`

这说明“更层级化子图更利于双曲方法”这一研究假设，并没有被当前结果直接证实，但已经出现了比全图更积极的方向性迹象。换言之：

**双曲方法在全图上明显不占优，但在更接近 typeclass / inheritance 结构的子图上，至少开始逼近强欧氏 baseline。**

### 16.16 下一轮子图实验应如何推进

基于这一轮真实结果，后续最值得继续推进的不是立刻扩大模型，而是进一步提高子图的语义纯度与评测可信度：

1. 优先把 `extends / instance_of` 从正则近似升级为更可靠的 Lean 元编程抽取。
2. 在该子图上补 8/16/32 维的 GCN / HGCN 公平低维对照。
3. 尽量扩大 typeclass-like 子图规模，避免当前 `176` 规模测试集带来的高方差。
4. 把“全图 vs 子图”的对照正式纳入论文叙事，作为几何适配性分析的一部分。

因此，到目前为止，最稳妥的主张应更新为：

**双曲方法是否适合 formal math graph，不应在全图上一刀切地下结论，而应结合子图结构分层讨论；当前 typeclass-like 子图上的结果，已经为这一分层叙事提供了第一轮工程证据。**

### 16.17 精确 Lean 元编程 hierarchy 子图：从 regex v1 升级到 precise v1

为进一步减少正则近似带来的语义噪声，当前已经在真实 `lean4-example` traced repo 上补了一条 Lean 元编程导出链路。其核心做法不是继续解析 `signature_text`，而是直接在 Lean 环境中读取：

1. `Lean.getParentStructures env declName`，精确导出结构/类的 `extends` 关系。
2. `Lean.Meta.isInstance declName`，精确识别带 `[instance]` 属性的全局实例声明。
3. 对实例声明再用 `forallTelescopeReducing + whnf` 读取其类型头部，只在头部真的是 typeclass 常量时才记为 `instance_of`。

这条导出链路首先在完整导入环境中得到：

- 节点数：`1308`
- 精确关系数：`1107`
- 其中 `extends = 19`
- `instance_of = 1088`

随后再与当前 `lean4_example_closed_world` declaration graph 做 join，并继续只保留 `class / instance / structure` 三类节点，得到新的 `typeclass_precise_v1` 子图：

- 节点数：`1233`
- 边数：`855`
- `uses = 765`
- `extends = 18`
- `instance_of = 72`

与 regex v1 相比，最重要的变化不是节点数变化，而是语义边显著收缩：

- regex v1：`extends_inferred = 120`，`instance_of_inferred = 105`
- precise v1：`extends = 18`，`instance_of = 72`

进一步检查发现，当前规范化 trace 中 `decl_kind = instance` 的节点共有 `86` 行，但去掉短名重复后只有 `81` 个唯一实例名；其中 `72` 个最终被 Lean 元编程成功识别并连上 `instance_of` 语义边。也就是说，regex v1 在这一小样本上确实存在明显过计；precise v1 更稀疏，但语义上更干净，也更适合作为后续“几何是否适配层级结构”的严谨实验底座。

同时也暴露出一个很重要的工程限制：当前 `normalized trace -> declaration graph` 这一步仍然大量使用短名，导致 `Context / State / map / bind` 这类常见名字发生碰撞。当前 precise join 已经做了“完整名优先、唯一短名兜底”的保守修复，但这还不是最终形态。投稿前必须把 `declaration_id` 升级到 fully qualified name 级别，否则图结构仍会混入同名冲突噪声。

### 16.18 precise v1 上的 8/16/32 维 GCN / HGCN 公平低维对照

在 `typeclass_precise_v1` 子图上，当前已经补做了一组同口径低维对照实验。协议如下：

1. 图：`typeclass_precise_v1`
2. 任务：边级 link prediction
3. 负例：`same_module harder negatives`
4. 维度：`8 / 16 / 32`
5. GCN 与 HGCN 均采用 `tie_all` 维度协议
6. HGCN v2 的 `decoder_hidden_dim` 也与输出维度绑定，避免“低维编码器 + 高维解码器”的不公平放大
7. 后处理：统一使用 `temperature scaling + validation-max-F1 threshold`

当前结果如下：

- `GCN-8d`：`test AP = 0.8177`，`calibrated test F1 = 0.7194`
- `GCN-16d`：`test AP = 0.9044`，`calibrated test F1 = 0.7576`
- `GCN-32d`：`test AP = 0.8988`，`calibrated test F1 = 0.8056`
- `HGCN-8d`：`test AP = 0.6928`，`calibrated test F1 = 0.7024`
- `HGCN-16d`：`test AP = 0.7759`，`calibrated test F1 = 0.7347`
- `HGCN-32d`：`test AP = 0.8314`，`calibrated test F1 = 0.7867`

这一轮 precise 图结果给出三个比 regex v1 更强的结论：

1. 在更精确的 `extends / instance_of` 子图上，当前仍然没有观察到 HGCN 整体超越强欧氏 GCN 的证据。
2. 在 `8d` 点上，HGCN 的校准后 `F1` 与 GCN 基本打平：
   - `GCN-8d calibrated F1 = 0.7194`
   - `HGCN-8d calibrated F1 = 0.7024`
   差距已经不大，但其 `AP` 仍明显更低，说明双曲模型在极低维下的阈值决策可以逼近欧氏，但排序质量仍不足。
3. 随着维度升高到 `16 / 32`，GCN 的优势重新变得明显，尤其在 `32d` 时：
   - `GCN-32d test AP = 0.8988`
   - `HGCN-32d test AP = 0.8314`
   - `GCN-32d calibrated test F1 = 0.8056`
   - `HGCN-32d calibrated test F1 = 0.7867`

因此，precise v1 当前支持的最稳妥结论是：

**精确 hierarchy 子图确实削弱了 regex 噪声，并让“8 维双曲接近欧氏阈值性能”这一现象更清楚，但它仍不足以支撑“精确层级图上双曲优于欧氏”的主张。**

接下来最值得继续推进的方向应是：

1. 在 precise 图上补 curvature scan，而不是只固定 `curvature = 1.0`。
2. 把 `uses` 与 `extends / instance_of` 再做更细的 edge ablation，检查双曲优势是否只出现在更纯的 hierarchy-only 图上。
3. 将样本扩大到更大 Lean/Mathlib 子集，降低当前小规模 split 的高方差。
4. 继续保留 calibration / threshold 协议，因为当前 HGCN 的 raw `F1` 仍会因概率刻度失配而被严重低估。 
### 16.19 precise v2 数据覆盖修复、GCN/HGCN 对照与 raw-logit 诊断

在完成 normalized trace 的可控 backfill 之后，当前 precise 子图的数据覆盖已经较 v1 有明显改善：normalized declarations 从 `20033` 增加到 `20119`，其中新增 `86` 个可恢复节点（`79` 个 instance，`7` 个 structure/class-like 节点）；`typeclass_precise_v2` 子图的节点数从 `2050` 增加到 `2136`，`instance_of` 精确边从 `880` 增加到 `959`，matched precise relations 从 `899` 增加到 `978`，dropped relations 从 `208` 降到 `129`。审计结果表明，剩余 `129` 条未匹配 relation 全部属于 Lean 元编程可见、但同时缺席于 trace 与 declaration index 的 helper/generated declarations，说明前一轮 `66 + 11` 可恢复覆盖缺口已基本被修复。

在统一的 `seed=42`、`same_module harder negatives`、`16` 维表征以及 `temperature scaling + validation-max-F1 threshold` 协议下，`GCN` 在 `typeclass_precise_v2` 上得到 `test AP = 0.8013`、`test AUROC = 0.7742`、`calibrated test F1 = 0.7123`；对应的 `HGCN v2` 得到 `test AP = 0.5992`、`test AUROC = 0.5982`、`calibrated test F1 = 0.6667`。这表明，在数据覆盖修复后，当前 precise 子图上的主要性能收益仍然由强欧氏 baseline 捕获，而不是由当前双曲模型产生反超。

针对 `HGCN v2` 进行的 raw-logit 诊断进一步说明，当前问题主要是“解码器分数尺度失配”，而不是“完全没有区分信号”。在 `test` split 上，其 raw logit 中位数为 `-8.4593`，`p95 = -1.6911`，最大值也只有 `0.2822`，因此在默认 `0.5` 阈值下的 predicted-positive rate 仅为 `0.0017`，直接导致 `raw test F1 = 0.0`。但其 `AP/AUROC` 仍高于随机，且经过校准后 `F1` 可恢复到 `0.6667`，说明模型并非完全失去排序能力。从 decoder decomposition 看，当前 `hgcn_residual_v2` 的得分可近似写为 `mlp(src,dst) + bias - scale * d_H(src,dst)^2`，其中 distance penalty 在 `test` 集上的均值对正例为 `-9.8036`、对负例为 `-11.5771`，确实提供了主要区分信号；但 MLP residual 分支对正负类的均值分别只有 `0.5622` 与 `0.5609`，几乎不提供额外 class-dependent margin，无法抵消 `distance^2` 项带来的大幅负偏移。因此，当前 HGCN 的失效形式更应被理解为“双曲距离惩罚主导下的 raw-score 严重失校准”，而不是“在 precise hierarchy 图上完全没有几何区分力”。这也意味着，后续 HGCN 迭代应优先集中在 decoder rescaling / normalization 与 residual margin 设计上，同时将 calibrated-threshold `F1` 继续作为默认汇报协议。
### 16.20 HGCN decoder rescaling 修复前后对照

在上一轮诊断中，`typeclass_precise_v2` 子图上的 `HGCN v2` 已经显示出一个明确的失效模式：其 raw logit 在默认 `0.5` 阈值下几乎全部落在负区间，导致 `raw test F1 = 0.0`，而经过 `temperature scaling + validation-max-F1 threshold` 后又可以恢复到 `calibrated test F1 = 0.6667`。这说明当时的主要问题并不是“模型完全学不到排序信号”，而是 decoder 中距离惩罚项的尺度设计导致严重失校准。进一步分解可见，原始 `hgcn_residual_v2` 直接使用 `edge_mlp(src,dst) + bias - scale * d_H(src,dst)^2` 作为打分，其中 test 集上 distance penalty 的均值约为 `-10.6904`，远大于 MLP 分支的均值 `0.5616`，最终把 raw logit 的 test 中位数压到 `-8.4593`，`predicted-positive rate @ 0.5` 仅为 `0.0017`，并迫使温度缩放学到一个异常大的 `temperature = 77.26`。

针对这一点，当前对 `hgcn_residual_v2` 做了第一版针对性修复：不再直接使用裸的 `dist^2` 作为惩罚信号，而是先将 `log(1 + d_H^2)` 做 batch 内 z-score 标准化，再经 `tanh` 有界化后乘以可学习的 `scale`，即把原先“无界且带固定量纲”的距离惩罚，改成“中心化、尺度受控、幅度有界”的距离信号。这样既保留了“距离越远惩罚越大”的排序方向，又显式去除了导致 raw logits 整体负漂移的量纲问题。按照与前一轮完全一致的协议（`seed=42`、`same_module harder negatives`、`16d`、相同 train/val/test split 与 calibration protocol）重跑后，新的 `HGCN v2 rescaled` 在 `typeclass_precise_v2` 上得到：`test AP = 0.6696`、`test AUROC = 0.6609`、`raw test F1 = 0.5944`、`calibrated test F1 = 0.6698`。与修复前相比，`AP` 从 `0.5992` 提升到 `0.6696`，`AUROC` 从 `0.5982` 提升到 `0.6609`，而最关键的 raw `F1` 则从 `0.0` 恢复到 `0.5944`。

从 score distribution 与 decoder diagnostics 看，这一轮修复确实击中了主要问题。修复后 test raw logit 的中位数从 `-8.4593` 回升到 `-0.1419`，`predicted-positive rate @ 0.5` 从 `0.0017` 回升到 `0.4353`，温度缩放参数也从异常的 `77.26` 降到 `1.68`。与此同时，distance penalty 的 test 均值从 `-10.6904` 缩小到 `-0.0216`，新的距离信号中心与尺度分别稳定在 `distance_signal_center = 4.1244`、`distance_signal_spread = 0.3618`，表明当前中心化与有界化过程已经显著缓解了距离项对总 logit 的病态主导。因此，这一轮结果可以支持一个更强的工程结论：此前 `HGCN v2` 的主要短板首先来自 decoder 的距离项尺度失配，而不是双曲表示在该子图上完全失效；经过 rescaling 修复后，双曲 baseline 的排序能力与 raw-score 可用性都出现了实质改善。

不过，这一轮结果也同样给出了一个清晰边界：尽管 rescaling 修复显著改善了 HGCN，但它仍未超过当前同协议下的 `GCN` baseline（`test AP = 0.8013`，`calibrated test F1 = 0.7123`）。因此，当前最稳妥的结论不是“修好校准后双曲已优于欧氏”，而是“在 precise hierarchy 子图上，双曲模型此前的主要失败确实包含 decoder 尺度设计这一可修复工程因素；修复后 HGCN 与强欧氏 baseline 的差距显著缩小，但尚未形成反超证据”。这使得后续研究路线可以更有针对性地推进到两个层面：其一，继续在 decoder 侧做结构改进，例如把当前 batch 级中心化升级为更稳定的 running-statistics / learnable normalization，或引入显式 residual gate，使 MLP 与距离项的相对权重不再完全由单个 `scale` 决定；其二，在任务与图结构侧做更细的归因实验，包括 `uses` 与 `extends / instance_of` 的 edge ablation、hierarchy-only 子图实验，以及更大规模 traced Lean/Mathlib 子图上的复现实验。前者用于验证“几何收益是否还能在更健康的解码器上继续释放”，后者用于验证“这种收益是否只在更纯层级结构、而非混合依赖图上才稳定出现”。

### 16.21 precise v2 上的 uses / instance_of / extends edge ablation

为进一步判断当前双曲 baseline 的瓶颈更接近“图结构不对题”还是“模型本身仍不够强”，当前在 `typeclass_precise_v2` 上补做了一轮 edge-type ablation。`typeclass_precise_v2` 全图共有 `2136` 个节点、`3733` 条边，其中 `uses = 2755`、`instance_of = 959`、`extends = 19`。基于这张图又导出了四个子图：`hierarchy-only = extends + instance_of`（`1090` 节点，`978` 边）、`instance-only`（`1076` 节点，`959` 边）、`uses-only`（`1838` 节点，`2755` 边），以及 `extends-only`（`25` 节点，`19` 边）。其中 `extends-only` 由于样本量过小，不再单独进行 link prediction 训练，而仅作为结构统计保留；否则 train/val/test 切分后的方差会远大于模型差异本身。

所有可训练子图都沿用与前文一致的默认协议：`seed = 42`、`same_module harder negatives`、`16d` 表征、`temperature scaling + validation-max-F1 threshold`。对照结果如下：

- `full precise v2`：`GCN` 得到 `test AP = 0.8013`、`test AUROC = 0.7742`、`raw test F1 = 0.6659`；`HGCN v3` 得到 `test AP = 0.6642`、`test AUROC = 0.6588`、`raw test F1 = 0.6463`。
- `hierarchy-only`：`GCN` 得到 `test AP = 0.7064`、`test AUROC = 0.6331`、`raw test F1 = 0.5992`；`HGCN v3` 仅得到 `test AP = 0.4628`、`test AUROC = 0.4502`、`raw test F1 = 0.4747`。
- `instance-only`：`GCN` 得到 `test AP = 0.7065`、`test AUROC = 0.6821`、`raw test F1 = 0.6547`；`HGCN v3` 得到 `test AP = 0.5009`、`test AUROC = 0.5120`、`raw test F1 = 0.4571`。
- `uses-only`：`GCN` 得到 `test AP = 0.7629`、`test AUROC = 0.7214`、`raw test F1 = 0.6567`；`HGCN v3` 得到 `test AP = 0.5616`、`test AUROC = 0.5703`、`raw test F1 = 0.5432`。

需要特别指出的是，在这轮 ablation 中，`HGCN v3` 的 calibrated `F1` 不能被直接解读为“排序能力接近 GCN”。在 `hierarchy-only`、`instance-only` 与 `uses-only` 三个子图上，校准后的 predicted-positive rate 分别达到 `1.0000`、`0.9895` 与 `0.9818`，本质上都已经接近“几乎全判正”的阈值解。因此，这一轮更可信的主指标应当是 `AP / AUROC / raw F1`，而不是单独看 calibrated `F1` 的数值。

这一轮 ablation 给出的结论相当明确。第一，若当前瓶颈主要来自“`uses` 边把层级结构冲淡了”，那么移除 `uses` 后，双曲模型相对欧氏模型的差距理应缩小；但真实结果恰好相反，`HGCN v3` 在 `hierarchy-only` 与 `instance-only` 上的表现不但没有变好，反而比全图更接近随机。第二，`HGCN v3` 在三类可训练子图里表现最好的反而是 `uses-only`，而不是理论上更接近层级结构的 `hierarchy-only` 或 `instance-only`。这说明至少在当前 `lean4-example` precise v2 数据、当前 link prediction 任务以及当前 decoder v3 设计下，“把图做得更纯层级化”并不会自动释放双曲几何优势。第三，`extends-only` 子图虽然从语义上最接近 inheritance DAG，但其规模只有 `19` 条边，尚不足以支撑有统计意义的模型比较；因此它目前只能作为“需要更大、更纯 inheritance 语料”的证据，而不能作为支持或反驳双曲优势的实验依据。

因此，这轮实验更支持如下判断：**当前双曲模型剩余的主要天花板，不再像是简单的“结构不对题”，而更像是“模型设计与任务形式仍不够强”**。更具体地说，当前问题至少包含三层：一是 HGCN 仍未学到足够稳定的边排序信号，尤其是在 `instance_of` / hierarchy 边上；二是当前 binary link prediction 任务本身可能不足以充分暴露双曲几何对 ancestor-like 结构的优势；三是 `lean4-example` 中真正纯粹的 `extends` 结构仍然过小，无法构成高置信度证据。基于这一点，后续最值得继续推进的方向应优先转向模型与任务两侧：其一，补 relation-aware / edge-type-aware 的 GCN-HGCN 对照，避免把 `uses`、`instance_of` 与 `extends` 完全压扁为同一种二元边；其二，把当前 link prediction 继续细化为更贴近层级结构的任务，如 ancestor ranking、parent prediction 或 typed link prediction；其三，再将同一协议迁移到更大规模、`extends` 更丰富的 traced Lean/Mathlib 子图上复验。只有在这些条件下，如果双曲方法仍然无法在 hierarchy-heavy 子图上形成稳定收益，才能更有把握地得出“结构假设本身不成立”的结论。

### 16.22 `full_precise_v1` 大图上下文上的 `parent_prediction` 对照

为了先验证“大图上下文”这一维度是否足以改变当前结论，当前进一步在 `lean4_example_full_precise_v1` 上补跑了 relation-aware `parent_prediction` 对照。该图保留了完整 `closed-world` declaration graph 的消息传递上下文，并显式注入 precise `extends / instance_of` 关系，共包含 `20119` 个节点、`86324` 条边，其中 `uses = 85346`、`instance_of = 959`、`extends = 19`。与 `typeclass_precise_v2` 相比，这一设置并没有增加层级边总量，而是主要把消息传递上下文从 `2136` 节点、`3733` 边扩展到更大的全图，因此它检验的核心问题不是“层级关系是否更丰富”，而是“更大的 declaration-level context 是否会帮助 parent-style hierarchy 预测”。

在与前文一致的协议下，`GCN` 在该大图上的结果为：`test AP = 0.8763`、`test AUROC = 0.8582`、`raw test F1 = 0.8108`、`calibrated test F1 = 0.7727`、`MRR = 0.1565`、`Hits@10 = 0.3125`；对应的 `HGCN v3` 结果为：`test AP = 0.8692`、`test AUROC = 0.8518`、`raw test F1 = 0.7902`、`calibrated test F1 = 0.7315`、`MRR = 0.0450`、`Hits@10 = 0.0729`。若与此前的 `typeclass_precise_v2` 对照相比，可以观察到两个同时成立的事实。第一，大图上下文确实显著改善了 HGCN 的二分类表现：其 `test AP` 从 `0.7210` 提升到 `0.8692`，`test AUROC` 从 `0.7331` 提升到 `0.8518`，`raw test F1` 从 `0.6974` 提升到 `0.7902`。第二，这种改善主要体现在“把正负边二分类分开”的层面，而没有转化为 parent-style 排序收益：HGCN 的 `MRR` 虽从 `0.0346` 升至 `0.0450`，但仍远低于 GCN 的 `0.1565`；`Hits@10` 也只有 `0.0729`，显著落后于 GCN 的 `0.3125`。相比之下，GCN 在大图上既保持了较高的 AP/AUROC，也在 ranking 指标上继续占优。

这轮结果给出的工程判断相当明确。当前不应把“大图上下文”误解为“已经为双曲方法提供了充分的新证据”。更准确地说，`full_precise_v1` 说明了更大的 `uses` 上下文确实能提升 HGCN 的边分类信号，但它并没有改变 parent prediction 的核心结论：在当前模型与任务定义下，双曲方法仍未表现出稳定的层级父节点排序优势。由于该图中的 `extends` 边仍然只有 `19` 条，真正的 hierarchy density 并没有实质提升，因此这轮实验更适合作为一个 go/no-go gate：**现在已经有足够证据说明，继续只在 `lean4-example` 上堆上下文，边际信息增益会明显下降；如果下一阶段目标是验证“双曲是否在更真实、更丰富的层级结构中占优”，那么转向新的 Mathlib trace 已经是合理且必要的下一步。** 但与此同时，这轮结果也提示，在切向更大 Mathlib 语料之前，最好先保留当前 relation-aware `typed link / parent prediction / ancestor ranking` 协议与 calibration 流程不变，把新 trace 只当作“数据规模与层级丰富度扩展”，避免同时更换任务、图构造与评测口径，从而导致结论不可归因。

### 16.23 真实小仓库 `plausible` 的端到端验证实验

为避免后续结论长期停留在 `lean4-example` 这类教学级小图上，当前进一步补做了一轮基于真实 Lean 仓库 `plausible` 的端到端实验。该实验的目标不是立刻追求最强结果，而是验证整条工程链路能否在真实仓库上稳定闭环：`LeanDojo trace -> XML/Lean 元信息归一化 -> closed-world declaration graph -> precise hierarchy join -> relation-aware parent prediction baseline`。在这一步里，工程上先修复了两个会直接污染标签质量的问题：其一，XML adapter 中将 `class` 与 `structure` 从 `CommandStructureNode` 里细分开，避免把 `Plausible.Shrinkable` 一类真实 typeclass 错记为普通结构；其二，Lean 侧 `importModules` 显式开启 `loadExts := true`，否则 persistent environment extension 不会被载入，`isClass` 与 `Meta.isInstance` 会系统性失真。这两个修复完成后，`plausible` 的真实 trace 已可稳定归一化为 `153` 条 declaration 记录，并进一步构成一张 `153` 个节点、`318` 条 `uses` 边的 closed-world 基础图。

在此基础上，当前再用 Lean 元编程导出了精确层级关系。原始导出环境中共得到 `3966` 个节点、`3379` 条精确 relation；但将其与 `plausible` 自身的 closed-world declaration 集做 join 后，可以保留下来的内部精确关系主要是 `instance_of`，而几乎没有有效的内部 `extends`。最终得到的 `plausible_full_precise_v1` 图包含 `153` 个节点、`386` 条边，其中 `uses = 318`、`instance_of = 68`、`extends = 0`；若只保留 `class / structure / instance` 三类节点，则 `plausible_typeclass_precise_v1` 进一步收缩为 `78` 个节点、`145` 条边，其中 `uses = 77`、`instance_of = 68`。这说明 `plausible` 是一个非常合适的**真实 typeclass-heavy 小仓库**，能够提供可信的 `instance_of` 层级信号；但它同时也暴露出一个重要边界：该仓库内部几乎不含可用于 inheritance 几何验证的 `extends` 结构，因此更适合作为“真实小仓库管线打通”和“instance/typeclass 关系建模”基准，而不是直接用来支撑“extends-rich hierarchy 上双曲优于欧氏”的核心论文结论。

在统一的 relation-aware `parent_prediction` 任务、`16d` 表征和同口径评测协议下，当前先在 `plausible_full_precise_v1` 上进行了第一轮真实 baseline 对照。`GCN` 的结果为：`test AP = 0.7285`、`test AUROC = 0.7500`、`raw test F1 = 0.5556`、`calibrated test F1 = 0.6316`、`MRR = 0.5650`、`Hits@1 = 0.4000`；对应的 `HGCN v3` 结果为：`test AP = 0.6047`、`test AUROC = 0.5400`、`raw test F1 = 0.0000`、`calibrated test F1 = 0.5455`、`MRR = 0.3152`、`Hits@1 = 0.1000`。这里需要特别强调两个解释。第一，这轮实验已经给出了一个积极的工程结论：**真实小仓库上的 trace、归一化、精确标签注入和基线训练链路已经完整跑通**，因此后续实验不再依赖纯 toy 数据。第二，这轮实验同样给出了一个克制的模型结论：在一个以 `instance_of` 为主、几乎没有 `extends` 的真实小仓库上，当前强欧氏 `GCN` 仍明显优于现有 `HGCN`；后者即便在校准后 `F1` 能恢复到 `0.5455`，其 `AP`、`AUROC` 与 ranking 指标仍明显落后。这意味着 `plausible` 更适合作为“真实数据可行性验证”和“typeclass-centric 任务入口”，而不应被过度解读为双曲几何已经失败或已经成功。更稳妥的下一步应是：保留当前这条已验证的小仓库真实管线，同时转向一个内部 `extends` 更丰富的真实 Lean 仓库，在不改变任务协议的前提下继续复验 GCN/HGCN 的差异，以判断双曲方法的潜在收益究竟受限于当前仓库结构，还是仍主要受限于模型本身。

若将本节进一步压缩为论文正文中的单段实验描述，可写为：我们在真实 Lean 仓库 `plausible` 上验证了从 `LeanDojo` trace 到精确层级图学习的端到端流程。修复 XML 侧 `class/structure` 混淆以及 Lean 环境加载时 persistent extension 缺失的问题后，`plausible` 可稳定归一化为 `153` 个声明，并构成一张含 `318` 条 `uses` 边的 closed-world declaration graph。进一步结合 Lean 元编程导出的精确关系，可得到 `153` 个节点、`386` 条边的 `full precise` 图，其中仅包含 `68` 条内部 `instance_of` 边而无有效内部 `extends` 边，说明该仓库更适合用作真实 `typeclass-heavy` 管线验证，而非 `extends` 丰富的 inheritance 基准。在统一的 `parent_prediction` 协议下，`GCN` 取得 `AP = 0.7285`、`AUROC = 0.7500`、校准后 `F1 = 0.6316`，明显优于 `HGCN` 的 `AP = 0.6047`、`AUROC = 0.5400`、校准后 `F1 = 0.5455`。因此，这一实验的主要意义在于证明真实小仓库上的 trace、归一化、精确标签注入与关系预测链路已经完整可复现，同时也表明：在以 `instance_of` 为主而缺乏 `extends` 的真实小图上，当前并无证据支持双曲模型优于强欧氏 baseline。
