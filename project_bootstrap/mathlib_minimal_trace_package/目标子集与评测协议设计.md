# 目标子集与评测协议设计

## 1. 目标子集选择

### 1.1 选什么

第一轮推荐目标模块前缀：

- `Mathlib.Algebra`
- `Mathlib.Order`

### 1.2 为什么不是直接全量 Mathlib

全量 Mathlib 当然最终值得做，但它不适合作为“最小可复现实验”的第一站，原因有三点：

1. tracing、normalize、抽图、precise relation 审计会同时放大成本。
2. 如果第一轮结果不理想，很难判断问题来自数据、任务还是模型。
3. 现在最需要验证的是“层级边密度提高后，relation-aware hierarchy 任务会不会真正改变双曲/欧氏对照结论”，而不是单纯增加 token 和节点数。

### 1.3 为什么优先 `Algebra + Order`

这两个模块前缀更适合最小实验包，主要因为：

- class / structure / instance 使用密度通常更高
- `instance_of` 链更丰富
- declaration graph 规模比 `lean4-example` 大很多，但又不像整库那样重
- 语义上和 typeclass/hierarchy 任务更对题

## 2. 数据切片策略

### 2.1 trace 前不切，trace 后切

建议第一轮采用：

1. 对固定 commit 的完整仓库做 trace
2. 生成全库 normalized trace 与 closed-world graph
3. 在 graph 层按模块前缀过滤出目标子集

这样做的好处是：

- tracing 路径最稳定
- 之后可以重复切不同子集，不必重 trace
- precise hierarchy 与 declaration index 也能复用同一份导出

### 2.2 模块过滤的边界

第一轮默认保留：

- 模块前缀命中的 declaration 节点
- 子集内部的 `uses`
- 子集内部可对齐到节点的 exact `extends / instance_of`

第一轮默认不保留：

- 指向子集外部节点的跨边
- 外部 declaration 作为消息传递节点

也就是说，优先采用 **closed-world 内部子图**，先保证可解释性，再决定是否做带外部上下文的扩展版本。

## 3. 固定抽图协议

### 3.1 declaration id

继续沿用当前全限定名协议：

- `declaration_id = source_commit::decl_name`
- `decl_name` 必须是全限定名

### 3.2 relation 类型

第一轮统一保留三类边：

- `uses`
- `extends`
- `instance_of`

其中：

- `uses` 来自 normalized trace 依赖
- `extends / instance_of` 来自 Lean 元编程精确导出

### 3.3 子图版本

建议版本命名：

- `mathlib_closed_world_v1`
- `mathlib_algebra_order_closed_world_v1`
- `mathlib_algebra_order_precise_v1`

## 4. 固定 relation-aware 评测口径

### 4.1 默认任务

第一轮统一跑三项：

1. `typed_link_prediction`
2. `parent_prediction`
3. `ancestor_ranking`

### 4.2 默认预测关系

- `target_relation_types = ["extends", "instance_of"]`
- `hierarchy_relation_types = ["extends", "instance_of"]`

### 4.3 默认消息传递关系

- `message_relation_types = ["uses", "instance_of", "extends"]`

### 4.4 默认负采样

- `negative_ratio = 1.0`
- `negative_strategy = "same_module"`
- `negative_fallback_strategy = "random"`

### 4.5 默认评测协议

- `seed = 42`
- `val_ratio = 0.1`
- `test_ratio = 0.1`
- `exclude_held_out_direct_edges = true`
- `temperature scaling + validation-max-F1 threshold`

## 5. 首轮对照矩阵

第一轮不追求模型花样，先做最小公平对照：

- GCN
- HGCN v3

每个任务各跑一组，形成 6 个 run。

## 6. 成功与失败判据

### 6.1 成功判据

如果出现以下情况，这个新 trace 子集就值得继续扩展：

1. `extends` 数量相较 `lean4-example` 有显著提升
2. `parent_prediction / ancestor_ranking` 的 ranking 指标稳定可读
3. HGCN 至少在某个 hierarchy-like 指标上出现比当前更合理的竞争力
4. precise relation 的 dropped/mismatch 比例可控

### 6.2 失败判据

如果出现以下情况，应优先回退排查数据，而不是继续堆模型：

1. precise `extends` 依然极少
2. 目标子图几乎只剩 `instance_of`，层级任务仍然退化
3. 大量 exact relation 无法对齐到节点
4. 新子图上 ranking 指标仍然主要由样本太小决定

## 7. 下一步扩展方向

如果第一轮成功，后续优先级建议是：

1. 在相同协议下扩到 `Mathlib.CategoryTheory`
2. 做 “closed-world vs. with-external-context” 对照
3. 在更大子图上继续做 typed parent / ancestor 任务
4. 再考虑更强的 relation-aware hyperbolic 模型
