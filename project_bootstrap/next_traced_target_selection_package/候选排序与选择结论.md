# 候选排序与选择结论

## 1. 这次到底在选什么

这次不是简单选“下一个能跑通 trace 的仓库”，而是选：

> **最有希望提供 `longest_chain > 4` 模块级 hierarchy 候选的下一个 traced 目标。**

因此判断标准与之前不同。此前 `plausible` 的目标是验证真实小仓库链路能否跑通，`batteries` 的目标是验证 coverage-aware precise hierarchy 能否恢复大规模 `instance_of` 信号；这一次的目标则是更强的结构性 gate。

## 2. 当前候选排序

### 第一名：`mathlib4` 的受控子域 trace

推荐方式：

- 不做 full trace 结论化复验
- 在 WSL 中用 `build_deps=false`、`num_procs=2`
- 先只把它作为“结构筛图目标”
- 首轮先看 `Mathlib.Algebra.*` + `Mathlib.Order.*`
- 若不够深，再转 `Mathlib.CategoryTheory.*`

为什么它排第一：

1. 从问题本身看，想要 `longest_chain > 4`，最自然的来源就是比 `batteries` 更大的真实层级库。
2. `Mathlib` 在类、结构、实例和 typeclass 继承上的密度，显著高于 `plausible` 与一般小仓库。
3. 之前 full Mathlib 失败，主要是因为走的是“Windows 上大规模 full trace + 全流程一把跑到底”的路线；这不等于 `Mathlib` 不适合作为**受控筛图目标**。
4. 当前脚手架已经具备 trace 后模块级切片、coverage-aware precise 注入、模块级 hierarchy 扫描这些关键能力，正好适合把 `Mathlib` 先当作“筛图母库”。

### 第二名：继续扩 `batteries`

这次不推荐继续把它当主目标，原因不是它没价值，而是它在当前问题上已经接近信息上限：

1. relation layer 全图 `longest_chain = 4`。
2. 模块级扫描后最佳候选也只到 `4`。
3. 多 seed 对照虽然在局部小图上已出现 HGCN 友好信号，但这些图的正例数只有 `26~28`，无法充当“更深 hierarchy”证据。

因此 `batteries` 适合保留为：

- 对照仓库
- coverage-aware 方法验证仓库
- 模块级 case study 仓库

但不适合作为下一轮“更深 hierarchy”主战场。

### 第三名：继续扩 `plausible`

不推荐，理由已经很清楚：

1. 真实 trace 链路已打通。
2. 内部几乎没有有效 `extends`。
3. relation layer `longest_chain = 1`。

它更适合做：

- 小仓库 trace 可复现实验
- typeclass / instance_of-only 案例

而不适合承担这次的目标。

## 3. 首轮子域为什么先选 `Algebra + Order`

这是一个兼顾“结构希望”和“工程风险”的折中：

1. 比 `plausible / batteries` 更可能包含更长的 class / structure / instance 链。
2. 比直接上 `CategoryTheory` 更容易控规模。
3. 与当前任务定义更对题：
   `parent_prediction / ancestor_ranking` 更容易在 typeclass-heavy 区域读出层级信号。

## 4. 为什么第二轮备选是 `CategoryTheory`

如果 `Algebra + Order` 跑完之后，模块级扫描仍然找不到 `longest_chain > 4` 的候选，那么更合理的下一跳不是回去继续磨模型，而是切到更层级化的子域。

`CategoryTheory` 被放为第二轮备选，是因为它更可能提供：

1. 更长的 inheritance / structure 链。
2. 更连续的层级上下文。
3. 更像“值得检验双曲几何”的结构。

代价则是：

1. 证明和依赖复杂度更高。
2. trace / precise exporter 更可能慢。
3. 数据审计成本更高。

## 5. 本轮的 go / no-go 条件

只有当首轮 `Mathlib.Algebra + Mathlib.Order` 模块扫描满足下面至少一部分，才继续把 GCN/HGCN 迁过去：

1. 出现 `longest_chain > 4` 的候选模块。
2. 候选模块 relation 规模明显高于 `batteries` 当前最优模块。
3. 候选模块的 `largest_relation_component` 不再只是十几到二十几节点的小组件。
4. `leaf_ratio` 明显低于当前 `batteries` 模块级候选。

如果这些条件都不满足，那么更稳妥的路线应是：

1. 切到 `Mathlib.CategoryTheory.*`
2. 继续只做筛图
3. 暂不迁移 GCN/HGCN 对照

## 6. 一句话结论

如果现在的目标是“优先找到值得做双曲 follow-up 的更深 hierarchy 模块”，那么下一个 traced 目标不该是继续换小仓库，而应是：

> **把 `mathlib4` 作为受控的模块筛图母库，先在 `Mathlib.Algebra + Mathlib.Order` 上做第一轮 hierarchy probe。**
