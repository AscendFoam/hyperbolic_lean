## 3. 如何解释这些指标

### 3.1 全图层面

- 巨型连通分量占比高、无向 cycle rank 很高：
  更像小世界/网状依赖图，而不是树。
- `delta_over_diameter_estimate` 较低：
  说明更 tree-like，但这只是近似 proxy，不应单独作为结论。
- `delta_over_diameter_estimate` 不低，且 cycle rank 很高：
  说明“直接期待双曲全图优势”风险较大。

### 3.2 relation-only 层面

- `condensation_longest_path` 很短：
  表明继承/实例层级本身不够深。
- `multi_parent_count` 很高：
  表明关系层更像 DAG/多继承网络，而非树。
- `largest_scc_size > 1`：
  说明 relation layer 中存在环或抽取异常，应优先审计数据质量。
- 层级图上 `delta_over_diameter_estimate` 明显低于全图：
  才能支持“纯 hierarchy 可能更适合双曲”的进一步实验动机。

## 4. 建议的判断门槛

如果同时出现以下现象，就不建议把“继续堆双曲模型”作为近期主线：

1. 全图和 relation-only 图都没有明显 tree-like 指标优势。
2. relation layer 的最长链仍然偏短。
3. `batteries` 这类 coverage-aware 图上，GCN 在 `parent_prediction` / ranking 上仍稳定优于 HGCN。

此时更合理的路线是：

1. 继续做图结构诊断和子域筛选。
2. 转向 relation-aware 欧氏模型、probing、检索等更稳妥方向。
3. 只在明确更 tree-like 的子域上保留双曲路线。

### 6.2 关键输出

- `candidate_graphs/<rank>_<slug>/`

### 6.3 如何解释模块级筛图结果

- `longest_chain`：
  这是最直接的“是否更深层”的信号。
- `largest_relation_component`：
  用来排除虽然有层级，但太碎的小组件。
- `leaf_ratio`：
  如果过高，往往说明仍然主要是浅层 instance-to-class 星状图。
- `hierarchy_score`：
  一个启发式综合分数，优先奖励更长链、更大主组件、较低叶子比例和更高 `extends` 占比。

### 6.4 当前应如何用这个结果做决策

如果筛出来的最佳候选仍然满足：

1. `longest_chain <= 4`
2. relation 子图规模只有几十个节点、几十条边
3. `leaf_ratio` 依然偏高

那么它更适合作为“结构案例分析”而不是“继续投入双曲模型对照”的主战场。

## 7. 模块级多 Seed 对照

### 7.1 为什么这里必须做多 seed

当前 `batteries` 模块级最佳候选都很小：

1. `Batteries.Control.AlternativeMonad` 只有 `28` 条正例关系。
2. `Batteries.Classes.Order` 只有 `26` 条正例关系。

在这种规模下，单次 `parent_prediction` 结果很容易被训练/验证/测试切分与初始化噪声放大，因此不应直接据此宣称 “HGCN 赢了” 或 “HGCN 彻底不行”。

### 7.2 运行多 seed sweep

例如运行 `AlternativeMonad` 上的 GCN 对照：

```powershell
& .\project_bootstrap\graph_diagnostics_package\scripts\run_dlenv_relation_seed_sweep.ps1 `
  -ConfigPath "project_bootstrap/graph_diagnostics_package/configs/relation_seed_sweep_gcn_batteries_control_alternative_monad_v1.json"
```

对应的 HGCN：

```powershell
& .\project_bootstrap\graph_diagnostics_package\scripts\run_dlenv_relation_seed_sweep.ps1 `
  -ConfigPath "project_bootstrap/graph_diagnostics_package/configs/relation_seed_sweep_hgcn_batteries_control_alternative_monad_v1.json"
```

`Classes.Order` 同理，改成相应的 `relation_seed_sweep_*_batteries_classes_order_v1.json`。

### 7.3 关键输出

- `aggregate.json`

- `per_seed_results.json`

### 7.4 当前已跑完的结论应如何解读

当前 `batteries` 上两张 depth-3 候选子图的五个 seed 对照显示：

1. `Batteries.Control.AlternativeMonad`：
   `HGCN` 的均值 `test AP = 0.8167` 高于 `GCN` 的 `0.7444`，`calibrated test F1 = 0.5567` 也高于 `0.4419`，但 `MRR = 0.1422` 低于 `0.1677`，且两者标准差都很大。
2. `Batteries.Classes.Order`：
   `HGCN` 在 `test AP = 0.8156`、`test F1 = 0.6876`、`calibrated test F1 = 0.6029`、`MRR = 0.4229` 上都高于 `GCN` 的 `0.6611 / 0.5543 / 0.3933 / 0.3868`。
3. 但这两张图的 relation 规模分别只有 `30/28` 和 `25/26`，且 `longest_chain` 也只有 `4` 与 `3`；因此更稳妥的结论不是“局部更深层模块已彻底坐实 HGCN 不占优”，而是：
   当前已经观察到局部模块上的分化信号，说明“大图浅层全局结论”不能直接外推到所有局部 hierarchy；但样本太小、方差太高，还不足以把它写成稳定规律。

### 7.5 用这一步来做后续决策

如果模块级多 seed 对照满足下面任一情况：

1. GCN/HGCN 在不同候选子图上给出相反结论。
2. 指标均值差距小于标准差量级。
3. 最佳候选的 `longest_chain` 仍不超过 `4`。

那么下一步更合理的是：

1. 把同一套模块级筛图协议迁移到下一个更大、层级更深的 traced 目标。
2. 优先寻找 relation layer 或模块子图里 `longest_chain > 4` 的候选。
3. 在迁移前不再把当前 `batteries` 局部结果写成关于双曲路线的最终判决。
